# Demo Plan

## Best demo scenario

Best scenario: **show a SQL-oriented remote exploration loop that stays inside the IDE and visibly reuses the same managed session for successive statements.**

Why this is the best fit:
- SQL gives the clearest `Run Current` story because the repo has explicit semicolon-based statement behavior for SQL work files (`LivySourceRouting.kt`, `LivyWorkFileMode.kt`, `LivyConsolePanel.currentRunnableText()`).
- The console result tabs, sessions tool window, and statement dialogs are all easy to explain visually (`LivyConsolePanel.kt`, `LivySessionsPanel.kt`, `ShowStatementsDialog.kt`).
- Managed-session reuse becomes visible through repeated session id references in the console context and result summaries (`LivyConsolePanel.updateContextLabel()`, `createOutputPanel()`).

Suggested live scenario:
1. Open `Livy: Open Work File`.
2. Pick a SQL profile such as "Analytics Prod".
3. Run `select 1 as a;` and show result tab `Session #X | Statement #1`.
4. Run `select 2 as b;` in the same work file and show that the new result uses the same `Session #X` with a different statement id.
5. Open the sessions tool window and show that the session is visible there.
6. Open the statements dialog for that session, inspect one statement, and reopen its code in the work file.

## Shortest happy-path demo

1. Open a work file from Tools.
2. Choose a SQL profile.
3. Run one statement.
4. Show the table result inside the same editor surface.
5. Mention that the same surface can now rerun more statements against the same managed session.

This is the shortest convincing path because it proves:
- profile selection;
- remote execution;
- result inspection;
- IDE-local loop.  
Evidence: `RunCodeViaLivyAction.kt`, `LivyConsolePanel.kt`.

## One failure / risk scenario worth mentioning

Recommended risk scenario: **changing connectivity assumptions breaks the story faster than IDE UX does.**

Best concrete example:
- a Livy endpoint with an untrusted certificate causes PKIX/truststore problems, and the repo explicitly treats that as an environment/runtime trust issue rather than a plugin feature (`README.md`, `plugin.xml`).

Why this is a better article-side risk mention than inventing a broken UX story:
- it is already documented by the repo;
- it warns readers about a real adoption filter;
- it does not falsely imply the plugin promises enterprise auth handling.

Alternative engineering-side risk to mention:
- if all managed sessions are busy and `killOldestIfFull` is disabled, the plugin throws a limit error rather than reusing unsafely (`SessionManager.createNewSessionOrThrow()` in `src/main/kotlin/com/queukat/livy_new/SessionManager.kt`).

## Demo notes for managed-session reuse

- The current UI does not appear to show an explicit "reused existing session" toast or decision explanation; reuse is inferred from the repeated session id in the console/result surfaces (`LivyConsolePanel.kt`, `SessionManager.kt`).
- For a stronger future article demo, the repo would benefit from an explicit reuse/creation explanation in the UI.  
  Evidence strength: medium; such a UX surface was not found in repository.

## А не фигню ли я делаю?

- Real user workflow focus: yes, the demo is a real open-run-inspect-reuse loop.
- IDE productivity tool, not platform: yes, the demo is intentionally small and editor-centric.
- Overclaiming security/auth or IntelliJ internals: no, the failure scenario sticks to repo-documented trust/connectivity limits.
- Is managed-session reuse really strongest: yes, the demo makes it visible without overselling it.
- Enough material for one focused article: yes, the current screenshots plus two extra dialog captures would carry the piece.
